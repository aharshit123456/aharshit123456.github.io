Building FamCare · Case study 02 · System design

A care marketplace on one boring backend

How a small team runs bookings, live tracking, payments and SOS for an in-home care service, and the handful of rules that keep it upright.

01The shape of the problem

A FamCare booking isn't an order that ships. It's a physical event that lasts hours: a trained caregiver travels to a family's home and looks after a baby or an elder while the parents are away. Along the way the system has to take money, choose and send the right person, show the family where they are, prove they've arrived, and react within seconds if something goes wrong.

That gives the backend four jobs that pull in different directions: money must be exactly right, state must never skip a step, real time must reach the right phone, and safety must work even when the rest is having a bad day. And it had to be built and run by a small team. Our answer is deliberately boring technology, plus a short list of rules we don't bend.

02The map

The backend is a single FastAPI service in modern Python, about a hundred domain packages (bookings, assignment, payments, wallets, pricing, SOS…), each split the same way: router, service, repository, models. It talks to Postgres in raw SQL through asyncpg, with no ORM, because we wanted every query visible in code review and in the slow-query log exactly as it runs. Transactions go through one helper, so "what's in this transaction?" always has one answer.

03A booking is a state machine, and the machine is a table

The allowed moves live in one explicit transition table, and every transition first takes a row lock on the booking, so two phones tapping at once can't both win. The guards are physical, not just logical: a caregiver can't mark arrived from across town, and a visit can't start until a face check passes and the family reads out a one-time code. Admins can override the table, and every admin action is written to an audit log by middleware.

Money gets three layers of defence, because payment providers don't always tell you what happened:

  • Webhooks are idempotent. Each provider event ID is stored with a unique constraint, so a replayed webhook is a no-op.
  • A reconciler closes the gap. Every five minutes it asks the provider about orders still marked "created". If the customer actually paid, the booking is activated, idempotently, as if the webhook had arrived.
  • Assignment is serialised. One checkout can fire the assignment step several times at once, so batch assignment runs under a Postgres advisory lock.

04Real time across many servers

The customer watches the caregiver travel, the caregiver gets new jobs, and ops watch everything. Each role has its own WebSocket channel; the admin panel uses Server-Sent Events, relayed through its own same-origin proxy so the browser never holds a token. With 2–10 API tasks behind the load balancer, the task holding a customer's socket often isn't the one that handled the caregiver's update. So every broadcast goes through Redis pub/sub, and every task delivers to the sockets it holds. Staging and production share one Redis, safely, because every key and channel is prefixed with the environment name.

05Conventions that delete whole classes of bugs

Money is integer paise. No floats, no rounding drift, no "₹99.99999". Wallet balances have a ledger behind them.

Phones are ten digits. Normalised at every entry point and backfilled once, so "+91…" and "0…" never create a second account.

Time is UTC, business days are IST. Stored as timestamps with a time zone, and converted only where a rule talks about "today".

One definition per question. Eligibility, pricing and feature flags each have one pure function that every caller uses. Case study 03 tells the story of what happened before we did that.

06Migrations treated like production code

With several engineers shipping schema changes every week, migrations were our most dangerous artefact. Raw-SQL migrations give us full control; the rules make that control safe:

  • New migrations ship with a test that applies them to a real Postgres. This started after a foreign-key bug that mocked tests sailed past.
  • A committed schema snapshot must match the migration chain. CI rebuilds the schema from scratch and compares, so the snapshot is a reviewable diff of what each PR does to the database.
  • Exactly one head, re-pointed at merge time. This came from an incident where two branches' migrations raced and a live database silently skipped a schema change. CI now renumbers diverged heads automatically, but never renames a migration that has already run anywhere.
  • Drift checks run inside the network. Every six hours a short-lived task compares the live databases with the code, so CI never needs database credentials.

07Infrastructure: from hand-built to Terraform, with zero drift

Production was first built by hand in the AWS console. Before adding anything, we mirrored it into Terraform without changing a byte: read-only discovery, generic modules, terraform import resource by resource, then plan again and again until it showed zero changes and zero forced replacements. Only then did we build staging. Today about 120 resource definitions live in code, and the rule is simple: no one-off console edits.

Staging: separate where it matters, shared where it's safe

Staging has its own ECS cluster and its own private database, which can scale to zero when idle, so tests can never touch production data. It shares production's network and load balancer through path rules: /api/* goes to production and /staging/api/* to staging. That needed no DNS changes and no second load balancer. Because the load balancer can't rewrite paths, the app simply serves under a configurable path prefix.

A few small decisions here carried more weight than they look:

  • CI owns the running image; Terraform owns the shape. Terraform ignores task definition revisions, after an apply once came close to rolling production back to an older image.
  • Scale on the database, not just CPU. The API scales out on CPU and on sustained database connection pressure, because CPU-only scaling missed a connection pool filling up. Every query also gets a default timeout, after an incident where the pool got stuck.
  • Pay for use, not for headroom. Serverless Postgres is billed for capacity actually used, so raising its ceiling costs nothing until it's needed. We also switched off an AWS recording service nobody read, which cut a noticeable line from the monthly bill.

08Changing behaviour without a deploy, or an app release

Feature flags are ours. They live in the database with four states (off, developers only, live, and targeted at named user groups), and one pure function evaluates them. We built them in-house rather than using our analytics tool's flags because server code, such as pricing, must get exactly the same answer as the app. Tunable numbers (geofence radius, cancellation window, kill switches) live in an admin-editable settings table.

The customer app updates itself. App store review takes days, so production builds are made with Shorebird, which can push Dart code patches over the air. Patches can't change native code or assets, so the patch pipeline refuses them unless someone explicitly opts in. Releases ship the full icon font so that using a new icon in a patch isn't an asset change. For changes a patch can't carry, the backend can mark old builds as unsupported, and the app shows an update sheet that can't be dismissed. Individual features can also require a minimum app build.

09Watching it: monitor the business, not just the servers

The monitor is its own service, not a job inside the scheduler, so if the scheduler is what broke, the monitor still runs. Every minute it checks three kinds of thing:

  • Read-only probes of the paths a customer takes: guest login, the deep health check, the catalogue, the version check, availability.
  • Business invariants in SQL: a payment captured with no booking, webhooks gone quiet, orders stuck without a caregiver, visits running long, the scheduler's heartbeat, database connections near the limit.
  • Traffic: error rates and 95th-percentile latency on login, payment, order and caregiver routes.

Alerts are debounced (two failures to go red, two passes to recover), go to Slack only when state changes, and tag the engineer who owns that area. Errors also flow to Sentry, logs to CloudWatch and metrics to a private Prometheus and Grafana.

Safety is a feature with its own budget

When a caregiver presses SOS, the backend opens a live voice conference: the caregiver's microphone goes live, admins are alerted in the dashboard and join muted to listen. The call ends itself after seven minutes, a deliberate cap so a forgotten SOS can't run up a telephony bill.

10What I'd tell a team starting out

  • Pick boring tools and sharp rules. FastAPI, Postgres and ECS are unremarkable. The rules (paise, one head, one eligibility function, one image) are what keep it working.
  • Turn every incident into a check. The migration tests, the drift check, query timeouts and database-based scaling each exist because something went wrong once.
  • Docs drift; tests don't. Even our own engineering guide had gone stale on migration counts and route counts by the time I checked it for this piece. The rules that matter are the ones CI enforces.
The idea worth stealing

Alert on business invariants, not just on servers. "A payment was captured but no booking exists" is the alert that protects your customers and your books, and a CPU graph will never show it.
