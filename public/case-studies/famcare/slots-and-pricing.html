01The problem: a promise made on one screen, kept on another

FamCare caregivers work rostered shifts out of hubs across the city, and families book them by the hour. Every booking crosses several pieces of code that each ask the same question: is there a caregiver who can do this visit? The slot list asks it to decide what to show. The instant-booking button asks it. Recurring bookings, the duration picker and checkout ask it before taking money. Then the matching code asks it again to decide who actually goes.

Each of them had its own SQL. Over months of fixes, rules about account state, check-in and missing roster rows were written slightly differently in each place. The results were the worst kind of bug for a marketplace: a slot shown that checkout then refused, or a slot sold that matching couldn't staff. None of it showed up in unit tests, because each query was correct by its own definition.

02One definition of "eligible"

The fix was structural rather than another patch. A single module now owns the definition of who may be considered for a booking, as composable SQL fragments: account state, hub and service, shift fit, the check-in policy, and conflicts with the travel buffer. Every caller builds its WHERE clause from those fragments instead of writing its own.

Three details made it stick:

  • The policy is written at the top of the module, with the date it was decided. Changing a rule means changing it there, then updating the scenarios. There's no second place to forget.
  • Shared numbers are shared constants. "Instant" means a booking that starts within an hour, and both checkout and the slot lists read that one value, so a slot is never offered that checkout then treats differently. The tolerance for a caregiver running over on the same family's previous visit is also one number, used by every conflict check.
  • The one deliberate disagreement is written down. A caregiver whose shift has started but who hasn't checked in is skipped by matching but still counts as capacity for a visit later that day. The exception is deliberate (hiding those slots is exactly what emptied a hub's slot list, below), and it's documented in the module and pinned by its own scenarios.
Rejected: fix each query until they agree. That works until the next change to any one of them. Sharing the code is the only agreement that survives new features.

03A test suite written as YAML worlds

A shared module only helps if something proves the callers really agree. So alongside it we built a scenario suite. Each scenario is a small world in YAML (caregivers, their rosters and existing bookings, a customer's history, one request) plus the outcome we expect:

# Later today, the caregiver's shift has started but she hasn't checked in.
- id: CHECKIN-002
  title: Not checked in, shift already started -> not matched, but still sold
  status: pass
  request: {service: nanny, start: "15:00", hours: 1}
  caregivers:
    asha: {checked_in: false}
  expect: {eligible: [], availability: bookable, browse: bookable,
           multiservice: bookable, batch_dates: bookable, tier_options: bookable}

The runner seeds each world into a real, migrated Postgres and runs the production code, not a re-implementation: the matching pool, ranking and pick, checkout's capacity check, and every slot-list endpoint (single service, all services, recurring dates and times, instant, the duration picker). It also covers back-to-back batches and the admin's one-click group assign.

Parity is the default assertion

Unless a scenario explicitly opts out, every slot endpoint's answer must match checkout's. A scenario written to test a check-in rule also proves that the slot list, the recurring picker and the duration picker agree with checkout about it.

Deterministic, or it doesn't count

Allocation code reads the clock, does travel maths and makes a seeded random choice, so a naive test would be flaky. The harness freezes time on both sides of the database boundary: in Python, and inside SQL by replacing now(). IDs are derived from the scenario ID, routing uses a straight-line estimate instead of a live engine, the random draw is seeded by the request ID, and every scenario runs twice and must give the same answer.

Known gaps are tests too

Some scenarios describe behaviour we want but don't have yet. They're marked known_gap with a sentence explaining why, and run as strict expected failures. If someone fixes the bug, the test goes red until the status is flipped to pass. A gap can't quietly close without being noticed, and a fixed bug can't quietly come back.

04Turning incidents and overrides into scenarios

The suite grew fastest when reality pushed back.

The morning a hub showed nothing

The first version of the shared policy required check-in for any booking dated today. One morning most of a hub's active caregivers hadn't checked in yet, so every service showed no slots, and the app silently fell back to tomorrow. We rewrote the rule within days: check-in is waived until a caregiver's shift starts, availability doesn't look at it at all for later-today visits, and instant visits still need someone checked in and on shift. Then we wrote out every combination as scenarios: booking type × check-in × shift state, capacity, the one-hour edge, other days, and batches. That's 71 scenarios for one rule, because it's the rule that broke.

Admin overrides became data too. We took a month of real cases (over two hundred) where ops overrode the system's suggested caregiver, wrote the distinct ones as scenarios and grouped the rest into patterns, always with the admin's choice as the expected answer. Where the system already agreed, the scenario passes. Where it didn't, the scenario is a known_gap whose text says how many real overrides it explains, so the backlog is ordered by evidence. One pattern, about one in five overrides, was a caregiver running slightly over on the same family's previous visit. That became the shared overrun tolerance above.

"No slots" is rarely a headcount problem

With availability finally trustworthy, we could ask a better question. About a quarter of slot-list views showed no open slots, which looked like a hiring problem. Replaying one hub over twenty days told a different story: only four of those days were a true shortage that an extra floating caregiver would have fixed. Most sell-outs were caregivers who were free but had no gap long enough once travel and buffers were counted. So the fixes were in the product (clear "Full" labels instead of unexplained greyed-out chips, and an "only N left" cue), not in hiring. Almost nine in ten customers who saw an empty day simply picked another date.

06Pricing idle time

Rostered caregivers are paid whether or not a family books them, and on average only about half of rostered hours were booked. With availability we could finally trust, the next question was whether price could fill some of the rest.

Why not surge pricing?

Surge was the first idea on the table. The data said no: on average caregivers were about half busy, and no day-and-hour cell reached 80%. The single tight hour, early evening, turned out to be a staffing gap (about a third fewer caregivers on shift), not a rush of demand. App taps also overstated morning demand by 1.5–2×. So surge stays at 1.0 in code, and the real opportunity was the opposite one: discount hours that would otherwise go idle.

The rule

Same-day slots get a drop made of two parts. The first is a gap-to-goal curve: the further a slot's utilisation is below a goal, the deeper the discount, shaped by an exponent k. The second is an idle ramp: each full hour without a new booking in the last hours before the slot adds a small step, and a step once earned is held: a new booking doesn't reset it.

Then come the guardrails, which matter more than the curve: a total cap, a per-hour price floor, and a check on the value of each booked hour for the hub's day. That last one replaced an average-order-value guard which, it turned out, blocked every drop on cheap one-hour bookings, even on completely empty slots. Admins can deepen or soften an existing drop but never invent one. Changing a pricing tier needs one-time codes from two phones. And a customer's price is held for ten minutes: a lower price applies silently, a higher one must be accepted.

Simulate first, with production code

Before any customer saw a drop, we replayed real rosters and bookings as they stood at each hour of the day, and priced every slot from 8 AM to 8 PM at every viewing hour from 4 AM. The simulator imports the same pricing engine as production, not a copy, and we checked the replay against the live simulator cell by cell: all 715 matched exactly.

The simulator is honest about what it doesn't know: it prices slots, but it can't say how customers react to a price. So we used it to bound the downside instead of predicting the upside. Replayed over two weeks with zero new demand, about a third of same-day orders would have received a drop, at an average depth of about 6%. To break even, dropped slots needed about 7% more booked hours, against a large pool of idle hours to fill. Production then started more conservatively than the defaults, hub by hub.

07What went wrong in pricing, and what we changed

The discount went to the wrong people

In the first eleven days, about half the discount went to customers who would have booked anyway, and a dozen daily regulars took over a third of all drops. Six in ten drop bookings were made less than two hours out, and nearly half came from customers on their eleventh booking or later. Only a handful were genuine win-backs.

Version 2 made drops about the customer, not just the slot: regulars don't get them, there's a lifetime cap per customer, and depth scales by behaviour cohort. Replayed on the same history, the same budget goes about 2× deeper to about half as many customers. We also set KPIs before claiming success: return on discount above 1.0, discount under a small share of revenue, idle hours down by at least 10%, and "price changed at checkout" errors kept rare. Without a holdout group, uplift is still unproven, and we say so.

One more lesson: the engine reads only the first hour's utilisation, so a three-hour window that's mostly empty can get nothing. That redesign is next.

08Making a drop visible, and keeping it

A discount the customer doesn't notice is just lost margin, and a discount that disappears between screens is worse: it reads as a bait-and-switch. Most of the app work went into the second problem. The server holds a customer's drop for ten minutes, and the app has to carry that held price through every step that can re-price a booking.

  • On the slot grid: each slot chip carries its drop, and the duration chips and the checkout strip show the drop for the length chosen.
  • Through the flow: the held price survives adding to cart, stepping the duration, editing the time on the payment screen and checkout's own re-pricing. Each of those was a separate bug where the drop quietly vanished.
  • At payment: the summary shows the base price and a separate price-drop row, in a receipt-style layout pinned by golden-image tests. If the price moved, a dialog explains it, and a higher price must be accepted.
  • The same rules as the server: no drop badge on twin bookings, instant checkout or recurring checkout, and a drop and a coupon never stack. The app clears the coupon and says so.
  • Measured end to end: price-drop analytics events across booking and checkout, including why a checkout failed and which price the customer was shown.

To decide how a chip should show a drop, I rendered four options as golden images from real slot data, so the team compared real prices rather than mock-ups: a small saving label (what shipped first), the price you pay with the old one struck through, a percentage tag, and the best price with a "Lowest" flag and a one-line reason above the grid. The review also caught two gaps worth fixing: the ten-minute hold had no visible countdown, and clearing a coupon had no explanation.

Notifications got the same treatment as pricing in version 2. The server sends one price_drop_available event per customer, carrying their cohort, their own drop percentage, how many drops they have left and whether this is the last one. The CleverTap campaign picks one of five messages from that, for example "we missed you" for a lapsed customer, a "plans changed?" note for someone who usually books a day ahead, or "last chance" when it's the final drop. No message has to guess who it's talking to.

09Flash sales: rarer, deeper, louder

The gradual engine tops out at a modest discount, and that's too weak to fill an evening slot that is still mostly empty a few hours out. So the next design does the opposite of the gradual engine. It's rare, deep and time-boxed, and it's loud about it.

Who gets it. Everyone except families who already book evenings regularly, since they would book anyway. That's the lesson of the first price drops, applied up front. Each customer gets at most one flash booking a fortnight, and at most one flash push a day and two a week.

Stored sales, not computed prices. A sale is a database row with its depth, spots and close time, not a price computed on the fly and not a coupon. The sale's ID is signed into the ten-minute price hold, so a client can't strip it to dodge the spot count or the fortnightly cap, and a customer who got the price in time keeps it even if the sale closes mid-checkout.

Where the customer sees it. The server emits a flash_sale_live event and a CleverTap journey sends the push ("⚡ 55% off tonight's 7 PM slot. Ends 6:00 PM, only 3 caregivers left"). In the app, a slim sticky strip is pinned under the Home header with a live countdown. The countdown runs on server time with the app's existing clock-skew correction, so it ends when the sale ends, not when the phone thinks it should. The strip refetches on open, on resume, when the countdown ends and every two minutes. Tapping it, or the push's deep link, opens booking for today with the sale slot already selected.

Why the strip comes before a sticky notification. The app strip ships as an over-the-air patch, so it can reach customers in days. A sticky notification in the phone's notification shade (an Android ongoing notification with a countdown, or an iOS Live Activity) needs new native code, which a patch can't carry, so it went out in a store release, driven by the same sale record and event as the push and the strip.

Status. Every part has shipped behind a feature flag: the backend (sale rules, data model, pricing hook with the signed sale ID, scheduler, APIs), the admin section (live sales, kill, force-open, per-hub settings, flash bookings labelled), the app strip with the booking and checkout UI and blanket golden coverage, and the sticky notification and Live Activity. Rollout goes to the team first, then one hub for a week, then the rest.

10What's next

  • Tests on the wire: the HTTP regression layer, so every bug fix adds a case that a real client request would hit.
  • Close the known gaps in order of how many real overrides each one explains.
  • Widen flash sales from the first hub to every hub, and tune depth and timing from what the first weeks show.
  • A real holdout group, so the next pricing result is a measured uplift rather than a replay.
The idea worth stealing

When several screens answer the same question, give them one function to ask, and write your tests as small worlds that assert they all agree. Then make every surprise from production, whether an incident or an admin override, into one more world. The suite becomes a record of everything your marketplace has promised.
