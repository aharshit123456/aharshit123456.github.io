A voice agent that only drafts

How we let parents talk for three minutes instead of filling in a form, without letting a language model write anything we can't take back.

01The problem

FamCare sends trained caregivers into homes to look after babies and elders, booked by the hour from an app. The first visit to a new family is the hardest one: the caregiver doesn't yet know that this baby calms down when you hum, refuses food if you insist, and must not have egg.

That knowledge lives in the Baby Passport, a care profile the parent fills in and the caregiver reads before the visit. The fields that matter most are the ones parents skip: open questions like "what helps calm them down?" don't get good answers typed on a phone with one hand.

So we asked: what if the parent could just talk? A three-minute conversation, and the Passport fills itself in.

Four constraints shaped everything that followed:

  1. Safety. A caregiver acts on what the Passport says. A model that hears "maybe egg" and writes allergy: egg, or hears nothing and writes no allergies, has created a safety incident.
  2. Language. Our parents mix English and Hindi mid-sentence. Their exact words ("zabardasti mat karna", don't force her) are often the most useful thing a caregiver can read.
  3. Cost. It has to be cheap enough to offer every parent, free.
  4. A small team. We can't babysit a real-time system. Any part of it can fail, and the parent should barely notice.

02The design

The parent taps Start talking in the app. Our backend opens a session, mints a room token and dispatches a voice worker into a LiveKit room. From then on, audio flows only between the phone, LiveKit and the worker. It never passes through our own servers. The worker talks back to the backend over a small internal API to load the session's context and post turns and drafts.

Inside the worker is a classic speech cascade: voice activity detection and a turn detector decide when the parent has finished speaking; a streaming speech-to-text model transcribes; an LLM decides what to say next; a text-to-speech model says it. We chose the cascade over a single speech-to-speech model because every stage is replaceable, every stage has a fallback, and the text between stages is something we can redact, log the shape of, and test.

03Five decisions that mattered

1 · Split the model that talks from the model that writes

There are two LLM roles. The interviewer runs the conversation: one question at a time, warm, short. It has no tools and can't save anything. After every parent turn, a separate extractor reads the redacted transcript and produces a structured draft of the Passport fields. It runs out of band, so the parent never waits on it.

The extractor's draft goes to the backend, and the backend shows it to the parent on a review screen. The only write into the child's record is the parent pressing Save, through the endpoint the manual form already used. The voice feature added zero new ways to change a child's profile.

The extractor follows rules, and the backend checks them again on every draft, because a prompt is a request, not a guarantee:

  • Allergy and medical tags only from the active list we send. Anything else goes to needs review, never to the nearest-looking tag.
  • Every field points at a real parent turn. No evidence, no field.
  • Phrases are kept verbatim, in the parent's language.
  • "She's about two" becomes an age, never an invented date of birth.
  • Allergies and outdoor permissions are always drafts. The parent confirms them on the next screen, every time.
Rejected: let the agent fill the form with tool calls. It's the obvious LLM design, and it puts the model on the write path. A wrong tool call would be a wrong record that a caregiver might act on before anyone noticed.

2 · Let slow drafts lose: every draft carries a sequence number

Extraction takes one to three seconds and runs after every turn, so drafts overlap. The draft for turn 3 can finish after the draft for turn 4, and if the backend kept whatever arrived last, the parent would see the form go backwards.

The worker numbers every turn and every draft; the backend keeps the highest draft number it has seen. It's a few lines of code, and it removes a whole class of race conditions without locks, queues or cancellation logic.

3 · Choose the model with evals, and weigh safety failures more than the score

Before picking a model we wrote an eval set of synthetic transcripts that encode the failures we were afraid of. The hedged allergy: "shayad anda", maybe egg, must not be tagged. An unlisted food (kiwi) must go to needs review instead of being mapped onto a listed allergy. A food-refusal phrase must come back word for word. "About two" must stay an age.

Two readings mattered more than the totals. First, direction: Nova Lite scored the same as Haiku, but its failures guessed a tag that wasn't said, which is the unsafe direction, so it was out despite being the cheapest. Second, a failure shared by several models (paraphrasing the food phrase) is a prompt problem, not a model problem, so we fixed the prompt instead of shopping for a model.

The rule since then: every bug found in the wild becomes an eval case before it's fixed. The suite has grown from 12 cases to over 100, across extraction, structured preferences and guardrails. Evals call real models, so they run before every prompt or model change rather than in CI; the unit tests, which need no network, run in CI.

4 · Model the cost before building, and find out what actually costs money

A three-minute interview speaks about 1,100 characters and makes about 28 LLM calls. We costed it per line from a real spike session and list prices before writing the production service.

This flipped our intuition. The LLM is 5–22% of the cost depending on the model, so we choose the LLM on quality, not price: the cheapest model that passes the evals saves pennies, while a wrong allergy costs trust. The biggest lever is on the speech side. Pre-rendering the fixed greeting and goodbye once saves about 17%, and running the extractor on every other turn saves about 8%. At pilot scale, fixed infrastructure is most of the monthly bill; by ten thousand interviews a month it's about an eighth.

5 · Failure is quiet: the call survives any one provider dying

The call depends on three outside AI providers at once. We assumed each would fail, and decided what the parent would experience when it did:

  • LLM: a chain of models and keys, best first; on our second key; then optionally a different cloud (Bedrock). A model that answers "quota exhausted" is marked unavailable and skipped on later turns instead of making every turn wait for it, and it's probed again in the background.
  • Speech: a second speech vendor sits behind the first for both STT and TTS.
  • All speech down: the call degrades to text. The agent's replies appear as chat, the parent can type, and the app is told through participant attributes so it can show the right UI.
  • Our own backend down: the interview carries on and the manual form still works. Nothing is lost that the parent can't type.
The bug that taught us this

When a speech-to-text account ran out of credit, the framework did what it was designed to do: recreate the failed stream every half second, and close the whole session after the fourth unrecoverable error. A billing problem would have hung up on the parent mid-sentence. We wrote the failing test first, then made the worker mark STT as down and stop the recreate loop, so typed answers and the agent's voice carry on.

04Privacy, built in rather than bolted on

Deterministic redaction, no LLM. Every turn that leaves the live call is redacted by code, not a model: phone numbers, emails, UPI handles, PAN numbers and links. It catches the forms people actually speak, like digits said in Hindi ("nau aath saat…"), "double nine", and "name at gmail dot com", while keeping ages, times and prices intact.

Safe against hostile input. Input is capped, every pattern has bounded repetition, and the digit scan is linear, so a crafted message can't make the regexes hang. Redaction runs off the event loop with a timeout; if it ever times out, the turn becomes [redacted] rather than leaking.

The agent knows less on purpose. It isn't told the child's name or any identifier. It uses a name only if the parent says it.

Nothing sensitive in logs. Transcript text and tags are never logged. Logs carry stable tokens like VOICE_DEGRADED stt that drive alerts, without content.

Typed input is guarded. Messages are cleaned, clipped and rate-limited. A client that floods the chat loses typed input for the session; voice and the form keep working.

05Built to change without an app release

The questions aren't hard-coded. Admins edit the wording, add follow-up hints, reorder, switch questions off, or add their own from the admin panel, and the worker loads them per session. Passport fields that a family has hidden are skipped automatically, and mandatory ones are always asked.

New behaviour arrives the same way. When we introduced structured preferences (pick-from-a-catalogue answers instead of free text), the backend started sending a preferences_mode per session. An absent value means the old mode, so a newer worker behind an older backend behaves exactly as before. The whole feature sits behind a feature flag that's off by default.

06What went wrong, and what we changed

  • Shared quota. The first spike borrowed an API key from our website chatbot, and the two competed for the same quota. Each service now has its own keys, plus a fallback key.
  • Deploys can cut calls. Fargate gives a stopping task at most two minutes, and a call can run longer. So a deploy has to drain workers before replacing them, never just restart them.
  • "Verbatim" is hard. Several models paraphrased the parent's phrase. That was a prompt problem visible only because the eval checked it word for word.
  • A small eval set is a screen, not a verdict. Twelve synthetic cases, one run each, can pass or fail a model by chance. We grew the set, and the next step is consented real transcripts.

07Results

We went from a spike to a feature-flagged build in under a week, and shipped it with the cost model, the evals and the fallbacks in place before the first parent used it. An interview takes about three minutes and costs about ₹9. The model chosen passed every screening case, and the design guarantees that the agent can't change a child's record: the worst it can do is propose a draft the parent rejects.

08What's next

  • Pre-render the fixed lines of speech, the single biggest cost cut.
  • Load-test how many concurrent calls one vCPU holds; it's the only large fixed cost and still an estimate.
  • Grow the evals from real transcripts, with consent, and run each case several times.
  • The same listening voice could become a private place for a parent to talk through caring for their child, with a human expert one tap away when real advice is needed.
The idea worth stealing

Put the LLM on the read side of your system, not the write side. Let it propose, make a human or deterministic code dispose, and check its rules again on the server. You get most of the magic, and your worst case becomes a draft nobody saves.
